# 实测记录

记录在真实环境里跑出来的结论，尤其是**与源码分析预期不一致**的部分。设计推导见 [`设计方案.md`](设计方案.md)，这里只放实际观测。

环境：codex-cli 0.147.0 / multica 0.3.17 / codex-lb（ghcr digest `3010b3c5`）/ Codex Pro 单账号

---

## 一、链路成立性

### 1.1 隔离性

同一台机器、同一个模型做对照：

| 命令 | 启动横幅 | 网关日志 |
|---|---|---|
| `codex` | `provider: openai` | 0 条新增 |
| `mcodex` | `provider: gw` | +1 条，按密钥正确归属 |

结论：`mcodex` 与用户的 `codex` 完全隔离，可并存。

### 1.2 multica 链路

`MULTICA_CODEX_PATH` 指向 mcodex 后派真实任务：

- daemon 日志：`agent command exec=/…/mcodex args="[app-server --listen stdio://]"` —— 参数完整透传
- mcodex 成功把 provider 注入 per-task `codex-home/config.toml`，与 multica 自己的 `# BEGIN multica-managed` 块共存
- codex 子进程环境同时拿到 `GW_API_KEY`（50 字符）、`CODEX_HOME`（per-task 目录）、`MULTICA_TASK_ID`/`AGENT_ID`/`WORKSPACE_ID`
- 任务正常完成，请求以 `ua=multica-agent-sdk/0.147.0` 出现在网关日志

### 1.3 提示词缓存

一次 multica 任务的连续三轮请求：

| 轮次 | 输入 tokens | 其中缓存 | 命中率 |
|---|---|---|---|
| 1 | 19,838 | 0 | 0% |
| 2 | 20,926 | 19,200 | 91.8% |
| 3 | 21,550 | 20,224 | 93.9% |

**经号池中转不丢提示词缓存**。这是方案经济性的前提条件。

## 二、与预期不一致的地方

### 2.1 超限响应不符合建议契约（重要）

设计方案要求网关超限时返回 `{"error":{"type":"usage_limit_reached",…}}`。**codex-lb 实际返回的是**：

```json
{"error":{"message":"API key total_tokens weekly limit exceeded. Usage resets at 2026-08-18T09:02:33Z.",
          "type":"rate_limit_error","code":"rate_limit_exceeded"}}
```

用 `weeklyTokenLimit=1` 的密钥主动触发后实测 codex 的行为：

- **只发 1 次请求，没有重试放大**（源码分析预测的 `RetryLimit` 分支成立，30 倍放大风险不存在）
- 但员工看到的是 `ERROR: exceeded retry limit, last status: 429 Too Many Requests`

**影响**：安全性没问题，可用性有问题——员工会以为是网络故障，而不是"我的额度用完了"。

**处置**：`poolctl doctor` 会检出并明确说明严重程度。要根治需要让 codex-lb 改用 `usage_limit_reached`。在那之前，应在员工须知里写明这条错误的真实含义。

### 2.2 超限请求不进 request_logs

被配额拦截的请求在网关的 `/api/request-logs` 里**查不到**（触发超限后网关日志零新增）。

**影响**：`poolctl usage` 统计不到"被拒绝了多少次"。要做超限告警不能依赖请求日志。

### 2.3 模型白名单用 403，会触发 6 次重试

`allowedModels=["gpt-5.5"]` 的密钥请求 `gpt-5.6-terra`：

```
HTTP 403 {"error":{"message":"This API key does not have access to model 'gpt-5.6-terra'",
                   "type":"permission_error","code":"model_not_allowed"}}
```

拦截本身有效，但 codex 对 403 会重试 6 次。请求都被拦在网关、不消耗上游额度，但会放大网关负载与错误日志。

**处置**：白名单必须覆盖员工日常使用的模型。`poolctl issue --allowed-model` 会打印这条提示。

## 三、对账能力的真实边界

### 3.1 对账头确实发出去了

用回显服务捕获 codex 实际发出的请求头，`env_http_headers` 完全按预期工作：

```
x-multica-task-id: task-abc-123
x-multica-agent-id: agent-def-456
x-multica-workspace-id: ws-ghi-789
```

同时 codex 自带这些标识：`session-id`、`thread-id`、`x-client-request-id`、`x-codex-turn-metadata`（含 installation_id 与 session_id）、`originator: codex_exec`。

### 3.2 但网关不记录任何自定义头

codex-lb 的 `RequestLogEntry` 没有请求头字段，实测记录里也没有。

**结论：task 级精确对账在当前网关下做不到**，需要 codex-lb 侧改造。头照发不误（无害，且网关将来支持时即可用），但不要在文档里承诺它能用。

### 3.3 conversationId 对 app-server 请求为空

| 请求来源 | conversationId |
|---|---|
| `codex exec`（手动） | 有值 |
| `multica-agent-sdk`（app-server） | **None** |

multica 侧记录的 `session_id`（如 `019f0000-0000-7000-8000-000000000000`）与网关的 `conversationId` **完全对不上**，无一命中。

### 3.4 可用的替代：requestId 前缀

同一会话的多次请求共享 `requestId` 的前 16 位：

| multica task | 请求数 | requestId 前缀 |
|---|---|---|
| `task-A` | 4 | `resp_aaaaaaaaaaaaaaaa…` |
| `task-B` | 3 | `resp_bbbbbbbbbbbbbbbb…` |

`poolctl usage --by-session` 基于此实现会话级归集。

⚠️ **这是逆向出来的规律，不是上游文档化的契约**，可能随版本变化。仅用于展示与粗对账，不要用于计费或权限判断。

## 四、安全承诺验证

| 承诺 | 实测 |
|---|---|
| 吊销立即生效 | 吊销后 **0.06 秒**内返回 401 `invalid_api_key` |
| 模型白名单拦截 | 403 `model_not_allowed`，有效（重试放大见 2.3） |
| 周额度上限 | 429，有效（契约问题见 2.1） |
| 密钥明文只返回一次 | 创建响应含 `key` 字段，后续查询只有 `keyPrefix` |

## 五、仍未验证

- **多账号 sticky 路由**：当前池内只有 1 个账号，无法验证多账号下的会话粘性与缓存表现。上文 93.9% 的缓存命中率是单账号结果，多账号池化后需要重测。
- `codex_rollout_budget_units` 对 Pro 订阅额度的换算关系。
- `MULTICA_CODEX_MULTI_AGENT=1` 开启后子 agent 的计量（codex 侧 delegate 的 TokenCount 被丢弃，网关侧应该看得见，未实测）。
- rollout `.zst` 压缩对长期 resume 会话的影响面。
